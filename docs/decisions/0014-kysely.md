# 0014: Kysely for database access and migrations

- Status: accepted
- Date: 2026-10-15

## Context

[0007](0007-sql-database-and-redis.md) makes MySQL 8.4+ and PostgreSQL 15+ first-class, with a query builder that supports both, migrations written with its schema API, portable types, and `SELECT … FOR UPDATE SKIP LOCKED`. It rules out an ORM and raw SQL outside a small dialect module. [0016](0016-sqlite-for-single-machine-installs.md) adds SQLite for development, tests and single-machine installs. The tables are few and well known ([data model](../architecture.md#data-model)), and the queries that matter are the scheduler's: claim tasks, update statuses in transactions, list jobs by cursor.

Options considered:

- **Kysely.** A typed query builder with official MySQL (`mysql2`), PostgreSQL (`pg`) and SQLite dialects. One query compiles to any of them. Its schema builder writes migrations once for all, and its `Migrator` runs them. Supports transactions everywhere, and `forUpdate().skipLocked()` on MySQL and PostgreSQL. No ORM, no code generation, no engine. Still in `0.x`: minor versions can break.
- **Knex.** Mature, with a schema builder and migrations for the three databases. Its TypeScript types are weak, so query results are mostly untyped, and the API is older (callbacks, a global instance).
- **Drizzle.** Typed, popular, but a schema is written per dialect (`mysqlTable`, `pgTable` or `sqliteTable`), and its migrations are SQL files generated per dialect. Supporting three databases means three schemas and three sets of migrations, which 0007 wants to avoid.
- **Prisma.** An ORM with its own engine and schema language. One schema targets one database provider, and migrations are SQL per provider.

## Decision

- `@eclair-js/server` uses **Kysely** with its `MysqlDialect` (`mysql2`), `PostgresDialect` (`pg`) and `SqliteDialect`, chosen from `DATABASE_URL`. Pin it to a minor version (`~0.29`) and upgrade on purpose.
- **SQLite runs on `node:sqlite`**, which comes with Node 24, rather than `better-sqlite3`:
    - `better-sqlite3` is the driver Kysely documents, and it's well proven. But it's a native addon, built or downloaded by an install script for each platform and Node version. Recent npm versions ask for approval before running install scripts, and the Docker image would need build tools as a fallback.
    - `node:sqlite` needs nothing to install and bundles a recent SQLite. Its API differs a little from `better-sqlite3`'s: statements take spread parameters, and there's no `reader` flag. A 20-line adapter in the dialect module gives `SqliteDialect` the interface it expects, using `columns().length > 0` as the `reader` flag. It was tried with Kysely 0.29: queries, transactions, WAL and JSON functions work.
    - If `node:sqlite` causes problems, switching to `better-sqlite3` only changes the adapter.
- **Table types** are hand-written TypeScript interfaces next to the migrations. A test runs the migrations on every database and compares the columns with these interfaces, so they can't drift.
- **Migrations** use Kysely's schema builder and run with its `Migrator`, from `eclair migrate`. They are TypeScript files, numbered, and additive within a major version ([deployment](../deployment.md#upgrades)).
- **The dialect module** (`src/database/`) is the only place that knows which database runs. It provides:
    - column types that differ: ids as `varchar(32)` with a binary collation on MySQL, timestamps with millisecond precision (`datetime(3)`, `timestamptz(3)`, ISO 8601 text on SQLite), JSON as `json` (text on SQLite), booleans as `0` and `1` on SQLite;
    - JSON reads and the equality filter on top-level `metadata` keys;
    - claiming tasks: `FOR UPDATE SKIP LOCKED` on MySQL and PostgreSQL, a `BEGIN IMMEDIATE` transaction on SQLite (see [0016](0016-sqlite-for-single-machine-installs.md));
    - the connection settings of SQLite (WAL, busy timeout, foreign keys);
    - the few statements the builder can't express portably.
- **No `RETURNING`.** Ids are prefixed ULIDs generated by Eclair before the insert, so nothing needs to be read back.
- Tests that touch the database run on all three, in CI's matrix.

## Consequences

- Queries are written once and checked by the compiler against the table types.
- Kysely's `0.x` status means reading its changelog on each upgrade. It is a small library with no engine, so pinning it is cheap.
- A feature only one database has stays out, or goes through the dialect module with an equivalent on the others, as 0007 says.
- The JSON helpers of each dialect (`kysely/helpers/mysql`, `kysely/helpers/postgres`, `kysely/helpers/sqlite`) are only used inside the dialect module.
- Kysely compiles `forUpdate().skipLocked()` even for SQLite, which rejects it. Only the dialect module builds locking queries.
- `node:sqlite` is synchronous: a query blocks its process while it runs. Queries on a local file are short, and long ones (pruning, usage aggregation) run in batches.
